## 4. 腳本與量測方式本身的問題

1. **WAL 檔案大小不會縮小**：SQLite checkpoint 完只會從頭重新使用 WAL，不會截短檔案，所以 12 組的「WAL 結束」都等於「WAL 最大」，看不出有沒有 checkpoint 過。能看出差別的是 `checkpoint_passive` 的頁數（`mainA` 580 對 `pool` 179,418）。
2. **「停止讀取後讓寫入繼續跑」這段只在一部分組別發生**：重播用 `--no-wait`，`pool1-10x-wyes`、`pool4-10x-wyes` 的寫入在第 2 輪就結束了，所以 `writes-only` 階段一個取樣點都沒有，第 2、3 輪其實是在沒有寫入的狀態下量的；`mainA-10x-wyes` 的寫入則一直到第 3 輪結束後還在跑（`writes-only` 5 個點）。也就是說，10x 有寫入的三組，第 2、3 輪的條件不相同。假設 2 的「沒人讀時」只能靠最後那一次 checkpoint 判斷。
3. **`replay_running` 是在每輪 5 個請求都結束後才檢查**，所以只代表「這一輪結束時」寫入還在不在跑，不代表整輪。
4. **CPU 取樣太稀**：每秒取一次，1x 的每輪不到 1 秒，所以只有 0–3 個點（`mainA-1x-wyes` 第 2 輪 0 個點），1x 的 CPU 數字不能用。另外 macOS 的 `ps -o %cpu` 是「最多一分鐘的衰減平均」（`man ps`），不是當下那一秒的使用率，會把前一輪的使用量帶進下一輪。
5. 取樣器在 `pool4-10x-wyes` 有一次間隔 2 秒（`ps` 和 `wc` 本身花了時間），少一個點。
6. 每組只跑一次，12 組照固定順序連續跑，沒有重複，也沒有換順序。第 1 輪包含 server 剛啟動、快取還是冷的狀態。
7. 機器不是閒置的（見「任務書可能寫錯或沒寫到的地方」）。
